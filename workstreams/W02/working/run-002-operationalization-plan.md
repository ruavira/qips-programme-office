# W02 Run 002 — Prototype Operationalization Plan

**Status:** READY FOR CCC AUTHORIZATION  
**Date:** 31 July 2026  
**Scope:** Months 1–2 only  
**Production lock:** PROHIBITED  
**Publication:** PROHIBITED

## 1. Objective

Once W02-01 is approved, convert the v0.9 programme spine into a tested, evidence-generating
months 1–2 learning system without implying that the final curriculum, assessment standard,
award, country adaptation or publication package has been approved.

## 2. Exit criteria

Run 002 is complete only when all of the following are present and verified:

1. Month 1 and month 2 outcome maps.
2. Session-level learning objectives using observable verbs.
3. eLearning storyboards and content maps.
4. Live-session facilitator plans and participant materials.
5. Coaching prompts, escalation rules and review-time estimates.
6. Learner artefact briefs with submission requirements and evidence rules.
7. Draft analytic rubrics and moderation notes.
8. Accessibility and low-bandwidth equivalents.
9. Synthetic-data or de-identified case packs where practice data is required.
10. Source, copyright, attribution and intellectual-property register.
11. Participant, faculty and coach timing logs.
12. Pilot feedback, defect register and disposition decisions.
13. Updated W02/W03 completion-blueprint assumptions.
14. Repository, Drive and Base44 synchronization evidence.

## 3. Work breakdown structure

### WP-01 — Architecture reconciliation

- Reconcile the v0.9 blueprint against every approved canon fact.
- Map the inherited 26 topics to the twelve-month artefact spine.
- Identify duplicated, missing and prematurely advanced content.
- Separate programme outcomes, month outcomes, session objectives and assessment criteria.
- Produce a traceability matrix from canon → outcome → learning activity → artefact → rubric.
- Record every unresolved assumption and its owner.

**Acceptance:** no month 1–2 component exists without a traceable purpose and evidence target.

### WP-02 — Month 1 learning design

- Define the month 1 performance outcome.
- Draft the problem-definition and improvement-opportunity artefact.
- Build the eLearning sequence, estimated time and knowledge checks.
- Build the live-session plan, facilitation script and debrief structure.
- Define the coaching touchpoint and escalation route.
- Draft the artefact brief, evidence requirements and rubric.
- Add worked examples and non-examples from varied settings.
- Create low-bandwidth, printable and screen-reader equivalents.

**Acceptance:** a learner can understand what to do, why it matters, what evidence to submit and how
it will be judged.

### WP-03 — Month 2 learning design

- Define the month 2 performance outcome.
- Draft the systems/process-mapping artefact.
- Build eLearning, live-session and coaching components.
- Define process-map conventions and evidence-quality checks.
- Draft the artefact brief, evidence requirements and rubric.
- Add worked examples from clinical, administrative and community settings.
- Create low-bandwidth, printable and screen-reader equivalents.

**Acceptance:** the month 2 package can be tested independently and also demonstrates progression
from month 1.

### WP-04 — Assessment and rubric engineering

- Define rubric dimensions, performance levels and observable evidence.
- Remove criteria that depend on prestige, English fluency beyond task need or institutional
  resources unrelated to competence.
- Add assessor guidance, edge cases and moderation rules.
- Test inter-rater interpretation using fictional submissions.
- Separate formative feedback from completion decisions.
- Record dependencies on W03 and prohibit final thresholds until W03 governance is resolved.

**Acceptance:** two reviewers can apply the draft rubric and explain disagreements using the same
criteria.

### WP-05 — Faculty and coaching feasibility

- Produce faculty-slot briefs for every month 1–2 component.
- Estimate preparation, delivery, review and follow-up time.
- Define which activities require accountable core faculty, guest contributors or coaches.
- Define maximum review load per coach and escalation thresholds.
- Test whether the proposed cycle is feasible at target cohort sizes.
- Feed capacity findings to W05 and W16.

**Acceptance:** no delivery promise is made without an explicit human-capacity model.

### WP-06 — Accessibility and delivery resilience

- Apply WCAG 2.2 AA design controls.
- Provide transcripts, alt text, structured headings and keyboard-operable interactions.
- Ensure all required learning can be completed under low-bandwidth conditions.
- Define downloadable, printable and asynchronous equivalents.
- Check language complexity, terminology support and mobile usability.
- Record any accessibility exception with owner, remediation and deadline.

**Acceptance:** accessibility is built into the source design rather than added after production.

### WP-07 — Evidence, source and IP control

- Register every external source with title, owner, date, URL and intended use.
- Distinguish quotation, paraphrase, adaptation and original content.
- Confirm image, chart, instrument and case-study permissions.
- Use synthetic or properly de-identified data for practice.
- Prohibit copied proprietary tools unless permission is documented.
- Link claims to the evidence register.

**Acceptance:** every externally derived element is traceable and legally reviewable.

### WP-08 — Prototype testing

Run at least three test modes:

1. **Expert walkthrough:** instructional designer, subject expert and governance reviewer.
2. **Cognitive walkthrough:** representative user attempts tasks while explaining decisions.
3. **Timed dry run:** participant, faculty and coach time is measured rather than estimated.

Capture:

- completion time;
- confusion points;
- accessibility failures;
- rubric disagreements;
- missing prerequisites;
- technical failures;
- unnecessary workload;
- country-context assumptions;
- safety, privacy or claims risks.

**Acceptance:** all critical and high defects have a disposition before prototype exit.

### WP-09 — Country adaptation

For Nigeria, Ghana and Pakistan:

- test terminology and examples;
- identify profession and system differences;
- identify data-availability assumptions;
- identify observership and workplace constraints;
- distinguish universal core from local adaptation;
- document what requires local expert validation.

**Acceptance:** no single-country example is silently presented as universally applicable.

### WP-10 — Completion-blueprint bridge with W03

- Map month 1–2 evidence to the provisional completion architecture.
- Identify which evidence is formative, summative or portfolio-supporting.
- Identify appeal, resubmission and moderation questions.
- Define what W02 can test before W03 decisions and what remains prohibited.
- Prepare the joint W02/W03 completion-blueprint input pack.

**Acceptance:** W02 prototype evidence informs W03 without either workstream blocking the other.

### WP-11 — Workspace synchronization and anti-drift control

- GitHub remains the authoritative governed source.
- Drive may contain human-review copies but not untracked decisions.
- Base44 mirrors status, decision requests, progress and links; it does not create canon.
- Supabase may later hold operational records only after an approved data model and access policy.
- Netlify and Vercel are deployment surfaces, never programme-truth stores.
- Every mirror records source path, Git commit, sync date, sync actor and divergence status.
- Any unverified divergence is marked DRIFT_OPEN and blocks publication.

**Acceptance:** another operator can determine which version is authoritative without relying on
memory or chat history.

### WP-12 — Verification and closeout

- Verify every exit criterion.
- Re-run YAML and repository integrity checks.
- Regenerate agenda and control-room outputs.
- Confirm no credential, secret or personal data was committed.
- Produce a run-002 verification report and council record.
- Update W02 state with evidence-based status.
- Submit only the decisions that require CCC authority.

| G3 Accessibility | Required equivalents and audit complete | Production lock prohibited |
| G4 Source/IP | Source and permission record complete | Asset removed or replaced |
| G5 Timing | Measured participant/faculty/coach time | Workload revised |
| G6 Assessment | Rubric test and moderation notes complete | Summative use prohibited |
| G7 Context | Three-country assumptions reviewed | Claim narrowed |
| G8 Synchronization | Mirrors tied to Git commit with no open critical drift | Publication prohibited |
| G9 Verification | PASS or PASS WITH NON-BLOCKING FINDINGS | CCC submission prohibited |
